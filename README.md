# باربي — Barbi Kids Commerce Platform

نظام تجارة إلكتروني موحّد لعلامة عراقية لملابس الأطفال (ولادة → 16 سنة): **متجر ويب PWA + كاشير POS + لوحة تحكم إدارية + API خادم مشترك للواجهات** — كلها على قاعدة PostgreSQL واحدة بتزامن لحظي.

## البدء السريع

```bash
git clone <رابط-المستودع-عندك>
cd barbi-kids
npm install
cp .env.example .env        # ثم عبّي DATABASE_URL على الأقل
npx drizzle-kit push        # إنشاء الجداول (يقرأ DATABASE_URL من .env)
npm run build && npm start
curl -X POST http://localhost:3000/api/seed   # بذر البيانات: منتجات + كوبونات + طلبات
```

## الخريطة

| المسار | لمن |
|---|---|
| `/` `/shop` `/product/[id]` `/cart` `/checkout` `/account` | المتجر (PWA قابل للتثبيت، RTL، دينار عراقي) |
| `/track` | تتبع الطلب برقم الهاتف بدون تسجيل دخول — خط زمني للحالة والقطع والإجمالي |
| `/pos` | شاشة الكاشير للفروع (باركود، دفع مقسّم، إيصال حراري 80mm، وضع Offline) |
| `/admin` | لوحة التحكم (الرمز التجريبي `2024`) — منتجات (مع رفع صور)، طلبات مع سجل حالات وإرجاع جزئي، زبائن، كوبونات بحد استخدام، توصيل، مخزون، الفريق والصلاحيات، سجل التدقيق، ورصد السوق (جوجل/Serper) |
| `/policies/returns` `/policies/privacy` `/policies/terms` | السياسات التشغيلية (تُراجع قانونياً قبل الإطلاق) |

## PWA والعمل بدون اتصال

- `public/sw.js` — عامل خدمة: التنقل شبكة أولاً مع نسخة محفوظة، الأصول الثابتة كاش أولاً، و`/offline` صفحة احتياطية.
- تسجيل العامل + دعوة التثبيت (`beforeinstallprompt`) في `src/components/PwaSetup.tsx`، وأيقونات 192/512 + `apple-touch-icon`.
- الـ API لا يُخزَّن أبداً: الأسعار والمخزون دائماً من الخادم.

## مفاتيح البيئة

كل الأسرار تُوضع في `.env` (محظور رفعها عبر `.gitignore`). راجع `.env.example` للقائمة الكاملة: قاعدة البيانات، هوية المتجر العامة (`NEXT_PUBLIC_BASE_URL` / `NEXT_PUBLIC_SUPPORT_PHONE` / `NEXT_PUBLIC_WHATSAPP_PHONE`)، أسرار الجلسات الثلاثة، Serper، مزود SMS، Upstash لحد المعدل المشترك، واعتمادات بوابات الدفع (زين كاش، FIB، كي كارد، آسيا حوالة، فاست باي، هواوي باي — الواجهة تعرضها، والربط المباشر ينتظر اعتماد التاجر). إعداد Drizzle (`drizzle.config.ts`) يقرأ `DATABASE_URL` من البيئة فقط.

## الصلاحيات وسجل التدقيق

- **حسابات إدارة فردية** في `/admin` ← «حسابات الإدارة» (للمالك): اسم + رمز PIN + دور. المالك يدير الحسابات، والمدير يدير المتجر بلا صلاحية عليها، وآخر مالك مفعّل محمي من الحذف. رمز `ADMIN_PIN` يبقى مدخلاً احتياطياً بصفة مالك.
- **حسابات موظفين** في `/admin` ← «الفريق والصلاحيات»: اسم + دور (كاشير/مشرف/مدير فرع) + فرع + رمز PIN (4–8 أرقام) يُخزَّن مُجزّأً بـ scrypt.
- **فتح الوردية في الكاشير** يتم باختيار الحساب وإدخال الرمز؛ وبعد وجود حساب لفرع، لا تُفتح وردية بالاسم وحده.
- **سجل التدقيق** في `/admin` ← «سجل التدقيق»: من فعل ماذا ومتى، منسوباً لاسم الحساب لا لـ«admin» مجهول.

## سلامة الطلبات والمخزون

- **idempotency**: كل طلب ويب وكل فاتورة كاشير تحمل `requestId`؛ إعادة الإرسال (أو مزامنة طابور الأوفلاين) تُعيد نفس الفاتورة ولا تخصم المخزون مرتين.
- **قواعد انتقال الحالة**: لا قفز من «قيد التأكيد» إلى «تم التسليم» ولا رجوع من حالة نهائية — تُفرض في الخادم على الإدارة أيضاً.
- **سجل حالات لكل طلب** في `order_events` (من → إلى، الفاعل، الوقت).
- **إرجاع جزئي**: إرجاع قطعة أو كمية من طلب مُسلَّم، باسترداد محسوب، واستعادة مخزون للجزء المسترجع فقط. عند اكتمال الإرجاع تصبح الحالة «مرتجع».
- **مخزون لكل مقاس**: كل مقاس له رصيده الخاص (`product_size_stock`)، فلا يُباع مقاس نافد حتى لو كان إجمالي المنتج متوفراً. البيع والمرتجع والتخزين يُحدّثون المقاس والإجمالي في نفس المعاملة، والواجهة تُعطّل المقاسات النافدة وتُظهر المتبقي.
- **التكلفة والربح**: سعر تكلفة لكل منتج (للإدارة فقط، لا يظهر في الكتالوج العام)، يُحفظ كـ«لقطة» على كل سطر فاتورة، ومنه تُحسب بطاقة «الربح التقديري» وهامشه لآخر 30 يوماً بعد خصم المسترجع.
- **كوبونات مضبوطة**: حد استخدام كلي (`maxUses`) وخيار «مرة واحدة لكل زبون» يُفحص برقم الهاتف.
- **إشعار الحالة**: عند تغيير حالة الطلب يُرسل SMS للزبون إن كان المزود مهيّأً، والرد يصرّح بالنتيجة (`sent/skipped/failed`) بدل الادعاء.
- **تصدير**: CSV للطلبات والزبائن من لوحة التحكم (UTF-8 مع BOM ليفتح تلقائياً في Excel بالعربية).

## التشغيل والنشر

**للتجربة السريعة (بلا قاعدة بيانات):** شغّل التطبيق بأمر واحد — الحاوية تكتشف غياب `DATABASE_URL` فتُقلع قاعدة PostgreSQL مؤقتة داخل الحاوية، تُنشئ المخطط، تبذر بيانات العرض، ثم تشغّل الموقع:

```bash
docker build -t barbi .
docker run -p 3000:3000 barbi
# http://localhost:3000  — لوحة التحكم /admin بالرمز 2024
```

تظهر لافتة «نسخة عرض تجريبية» في هذا الوضع، والبيانات تُصفَّر عند إعادة التشغيل.

**للإنتاج (قاعدة دائمة):**

```bash
cp .env.example .env
docker compose up -d --build     # PostgreSQL + التطبيق، DATABASE_URL يشير إلى خدمة db
./scripts/backup.sh              # نسخة احتياطية مضغوطة + تشذيب آخر 14
```

- `Dockerfile` لصورة التطبيق، و`docker-compose.yml` للإنتاج، و`docker-entrypoint.sh` يفصل الوضعين.
- عند نمو المخطط: `npm run db:generate` ثم `npm run db:migrate` بدل `push` على قاعدة فيها بيانات.
- النسخ الاحتياطي يحتاج `pg_dump` على الجهاز وعلى جدولة يومية (cron) في الإنتاج.
